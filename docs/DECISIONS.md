## 2026-10-14 — Repair audit contracts

Use MediaRecorder until a real container muxer/audio path replaces raw encoded-byte concatenation. Keep fragment bytes on disk and require durable journal/receipt transitions. Server assigns participant/source/track identifiers and enforces ownership at every upload operation; grants are delivered only to their participant. Host bootstrap and management remain on loopback and are never available through Serve/Funnel. Snapshot expected recorders atomically with the take. Export only when each expected recorder and every registered track is assembled; missing media and every output-stage failure are errors. Publish outside personal Movies by default under the configured data directory. Advertise measured coarse alignment until timestamped references and independent capture-timing validation justify a stronger claim.

## 2026-10-15 — explicit private-host identity and portable delivery

Keep local-only management as the default. Optional remote owner management uses explicit exact Tailscale identity and HTTPS origin configuration behind loopback Serve, with tailnet-client and Funnel-negative checks. A guest link conveys StudioLink admission only; it never enrolls devices or carries Tailscale auth keys. Do not automate sharing the entire host or reuse owner account credentials in invitations.

Provide an authenticated editor-package ZIP from published outputs, not arbitrary filesystem downloads. FCPXML 1.10 uses relative media-rep URLs, measured media duration and participant video/audio angles; the older generated one-hour timeline and host-only FCPXML links were incorrect for cross-machine delivery. Retain legacy xmeml with explicit relinking instructions. Schema validation and playback decode do not establish actual editor import or acoustic sync accuracy.


### 2026-10-16: first-permission HD and truthful portrait timing

A real second-account Safari phone take uploaded correctly but recorded only 480×640. Camera IDs can be hidden before permission; the previous no-ID branch requested unconstrained video. Always request ideal 1920×1080 at 30 fps, refresh device labels after permission without reacquiring, and report actual lower resolution rather than implying HD.

The phone also exposed that exported portrait assets were declared as 1080p landscape. Probe and retain native dimensions in manifests and asset format metadata. CFR video consistently resets its own PTS to zero; preserve the original video's leading offset relative to the container in its host-clock timeline placement, scaled by the same drift factor. Isolated audio remains on its original origin. This preserves container A/V relationships but is not acoustic fine alignment or measured physical lip-sync.


### 2026-10-16: regenerating editor packages preserves prior exports

A real stopped phone take exported once, but regeneration failed because publishDir rejected its existing destination. Stage and complete the new package first; retain the entire previous directory beside the current one with a unique `.previous-` suffix, then rename the staged package into place. Failed copies leave the prior package untouched, and a failed final rename restores it. Existing non-directory/symlink destinations still fail closed. No original uploads or editor-added files are deleted.


### 2026-10-16: native NLE import is an acceptance gate

DTD-valid FCPXML is insufficient: Resolve 21.0.4 crashed importing the phone multicam package. Keep FCPXML explicitly experimental until Final Cut/native compatibility is demonstrated. Resolve uses the separate-track FCP7 XML. Native import also demonstrated that complete sequence duration, per-clip duration/rate, and canvas metadata are needed to avoid an empty timeline. Preserve source geometry and aligned edit offsets, URI-encode and XML-escape media paths. Imported downloaded media still needs relinking when host absolute paths differ. Independent acoustic interdevice sync remains a separate acceptance check.


### 2026-10-16: authenticated socket resume and native-proven multicam audio

Reuse the signed in-memory upload grant in Hello to resume an admitted identity without changing privileges, persisting credentials in browser storage, or minting arbitrary caller-selected identities. Keep capture/upload independent of socket retry; reconcile missed Stop after resuming. Stale sockets cannot unregister replacements. Private HTTPS and invitation authorization remain required.

Resolve 21.0.4 requires multicam tcStart/tcFormat despite their optional DTD status. Native roundtrips also demonstrate it ignores gap-backed video and retains only one selected audio angle. Use direct camera-only multicam angles with all isolated microphones connected on the project timeline. Preserve each microphone's timing and full duration independently of video switches. Resolve native roundtrip with local media confirms two cameras and two enabled microphones; Final Cut acceptance remains separate.


### 2026-10-25: call senders are capped per room size; failed media is replaced, not ICE-restarted

The call used to send the full 1080p capture with no sender limits, which competed with progressive uploads. Recording still uses that full-resolution capture (ADR-006). Only the RTCRtpSender is limited: 720p/1.5 Mbps for 1–2 participants, 540p/900 kbps for 3–4, 360p/500 kbps at 24 fps for 5 or more, with maintain-framerate and Opus at 64 kbps. The client re-applies these limits when the number of remote participants changes.

Media recovery rebuilds the client's PeerConnection and re-offers it. The SFU treats a second offer from the same participant as a replacement: the old peer is detached and closed, and the other participants renegotiate in both directions. We rejected ICE restart on the existing peer. Server-driven renegotiation means the server may hold an unanswered offer (glare would need rollback), ICE restart can't recover a broken DTLS/SRTP association, and a `failed` server peer is already removed. Replacement needs no new protocol messages. The client ignores server offers while its own offer is pending, and those offers belong to the replaced peer. Call mic/camera state is a new `participant_state` message relayed by the hub. Remote track `mute` events are unreliable here because disabled tracks keep sending black frames or silence.


### 2026-10-25: a host mute silences the call, not the recording; collaboration state is in-memory

**Host mute (Meet semantics).** A host's `mute_request` asks the participant's client to stop sending its microphone to the call. The local ISO recording keeps the raw microphone, because editors want every isolated track intact and a host mute is about the live call (noise, crosstalk), not the record. To make that possible the call now sends a *clone* of the microphone track (`web/src/lib/callmic.ts`); recorders and the level meter keep the original. Honesty rules: the muted participant is told immediately that the host muted them in the call and, if a take is running, that their own recording still captures the microphone and how to stop it ("Mute mic + recording"). Self-mute is unchanged: it silences both the call and local recording. Unmuting after a host mute only restores the call. The host cannot unmute anyone. Rejected: host mute also stopping the recording (silently loses ISO audio the editor may need) and server-side muting in the SFU (the participant would not know, and their UI would lie).

**Remove** reuses the deny path: the participant's store status becomes `denied`, which already revokes the upload grant, TURN relay authorization and resume. Their client stops sharing and stops local capture; un-uploaded chunks stay in their browser (the host is told this in the confirmation dialog). **Lock** is per-session, in memory, and refuses new hellos (no join request reaches the host) while admitted participants still resume with their signed grant and the host is never locked out.

**Chat, hands and the lock live only in hub memory** for the daemon's lifetime (last 200 messages per session). They are not written to SQLite, not part of exports, and never logged. Persisting chat can come with persistent rooms.


### 2026-10-25: screen share renegotiates the existing PeerConnection; the client is the polite peer

A screen share adds tracks mid-call. Media recovery already re-offers from a *new* PeerConnection, which the SFU treats as a replacement. Using that for every share start/stop would drop and re-add everyone's media, a visible glitch for all participants. Instead the client renegotiates its existing PeerConnection: `sdp_offer` with `renegotiate: true` goes to `SFU.HandleRenegotiation`, which never replaces the peer. Both sides may now offer, so glare is resolved with perfect-negotiation roles. The SFU is impolite: while its own subscription offer is outstanding it drops the client offer without replying. The client is polite: it is necessarily in `have-local-offer` when that server offer arrives (same ordered socket), so it rolls back, answers, and re-offers once stable. A renegotiation unanswered for 10 s falls back to full media recovery, which republishes the share. Screen tracks go on fresh `sendrecv` transceivers. `addTrack` would recycle an idle transceiver the SFU created for a subscription, and Pion does not receive on m-lines it offered (observed in the browser test).

The SFU tells camera from screen by **declared track IDs** (`source_add {kind: screen, trackIds}`, sent before the offer on the same socket), not by SDP heuristics, and forwards screen tracks with stream ID `<participantId>_screen`. One presenter per room (Meet's default). A second `source_add` gets `action_error conflict`; takeover can come later. The host's `screen_stop` is enforced on the server: the hub unpublishes the share in the SFU first, then asks the presenter's client to stop. Screen/system audio never feeds the reference recorder, which stays the microphone (the alignment reference). Rejected: re-offer-as-replacement (glitches everyone), a second PeerConnection per share (doubles ICE/DTLS and breaks one-peer-per-participant routing), and simulcast/SVC for screens (not needed at ≤4 participants).

### 2026-10-25: a shared screen is recorded as its own late source on the presenter's device

While a take records, the presenter's screen is recorded locally from the `getDisplayMedia` capture track, never from WebRTC-received media (guardrail). It uses its own MediaRecorder, OPFS chunks, upload queue and sidecar, registered as a `screen` source with `POST /takes/{id}/tracks {source: "screen"}` whenever the share or the take starts. The take's expected-recorder snapshot is unchanged. A screen track is optional and may start late or stop early, so it never satisfies or creates a participant's expectation (`ListMissingTakeParticipants` ignores screen sources). Like any registered track it must still assemble before export, so a failed screen upload needs recovery like any other track. Its offset comes from its own sidecar `recorder-start`, and the export gives it its own multicam angle ("<Name> Screen", manifest `source: "screen"`), with shared audio as a separate WAV. Postproc conforms screens onto a fixed even canvas with `-reinit_filter 0`. Windows can be odd-sized (rejected by 4:2:0 H.264) and can resize mid-recording, and a rebuilt filter graph restarts `STARTPTS`, so CFR would drop every frame after the resize (reproduced in `TestLateScreenShareExportsAsOwnAngle`).

### 2026-10-25: device switching is locked while a take records

Switching camera or microphone mid-call uses `replaceTrack` on the call sender and swaps the track in the capture stream. A running MediaRecorder cannot follow a track swap in its stream, and the PCM recorder is bound to its own microphone stream. So while a take is arming, recording or stopping, the Devices popover disables camera/microphone with a plain explanation ("locked while a take is recording, so your recording is not interrupted. Stop the take to switch."). Speaker output (`setSinkId`) stays available because it never touches capture. Rejected for now: finalizing the current recorder segment and starting a continuation track. It needs multi-segment tracks in the store, gap handling in alignment and export, and new completeness rules, which is far more failure surface than the rare need to change devices mid-take. Between takes, switching is instant and needs no rejoin.
### 2026-10-25: native host app supervises the daemon; the call stays in the browser (ADR-015, SL-P2-1)

**Shell.** The zsh launcher is replaced as the bundle executable by a Swift 6 app (`macapp/`, SwiftPM, no Xcode project, macOS 14+). It keeps the launcher's safety rules: it reuses a daemon only on an exact product + build match and never signals anything else on the port. It adds supervision: crash restart with backoff 1→30 s, giving up after more than 5 crashes in 2 min. It never kills an unresponsive daemon while the last known state is recording, live or unknown. Settings restarts wait for idle. Quit stops the daemon and warns first if work is in progress. The launcher stays in `Contents/Resources` as a headless fallback. The Go systray in ARCHITECTURE §11 was never built and is dropped.

**State channel.** The app needs recording, live and waiting-guest state for every session, including sessions created in the browser. Those sessions have host tokens the app never sees, so a host WebSocket subscription would need a new credential anyway. We added `GET /api/v1/desktop/state`. It is direct-loopback only (it rejects Serve/Funnel/forwarded headers, any `Origin` and non-loopback `Host`), takes a bearer token from the 0600 `<data-dir>/.desktop_token`, and returns no credentials. The app polls it every 2 s, which also drives notifications. Rejected: reading SQLite from the app (it couples the app to the schema and misses in-memory call state), and a desktop WebSocket (more moving parts for a 2 s status refresh).

**Tailscale.** The app runs only argv-built CLI commands. Read-only status commands run automatically. Serve/Funnel changes run only after the user clicks, sees the exact commands and confirms, and then the result is re-read and verified. The app never runs `reset`. Public mode is Funnel :443 to the app plus TLS-terminated TCP :8443 to TURN through Funnel, with the daemon restarted with `--public-url … --funnel-turn` (ADR-004/013).

**WKWebView spike → browser by default.** On this Mac every studio API passes in WKWebView on the loopback origin: secure context, MediaRecorder WebM/MP4, OPFS `getDirectory` + `createWritable`, AudioWorklet, WebSocket and RTCPeerConnection with media. With WebKit mock devices, `getUserMedia` reaches the native permission delegate and yields 1280×720 + audio. Real-device `getUserMedia` could not be confirmed: the run was unattended with the screen locked, TCC stayed `notDetermined`, and WebKit asks TCC before the delegate. `navigator.storage.persist()` also returns false. Because a required capability is unverified, the call stays in the default browser (Chrome recommended) and the main window is a native control center. The in-app studio ships as an opt-in beta setting. To make it the default, rerun the probe attended until `getUserMedia=yes` and complete a full in-app take with uploads. Raw results: `docs/research/2026-10-25-wkwebview-probe*.json`.

**Deferred.** Sparkle (it needs an appcast host and an EdDSA key; we add no hosted service of our own) and an app icon.

### 2026-10-25: persistent rooms are durable links over ordinary sessions; the link secret is derived, not stored (SL-P1-5)

**Model.** A room is a row (`rooms`) with a name, an immutable slug and settings; each meeting opened from it is an ordinary session with `room_id`. Recording, takes, uploads and exports are untouched, and an instant meeting is still a session with no room. "Live" is the room's session with `ended_at` NULL; a mutex makes "open the room" create at most one. Guests are sent to admission only when the host is admitted in the call (`Hub.HostConnected`), so a join request always has someone to answer it. Rejected: one long-lived session per room (takes, chat and admissions from different weeks would mix, and "end meeting" would mean nothing), and putting the room into the hub only (it must survive restarts).

**Link secret.** The guest link must be shown again ("copy link" any time) yet stored hashed. Secret = HMAC-SHA256(daemon secret key, room ID ‖ nonce). The database keeps the random nonce and SHA-256(secret); the daemon recomputes the link for the dashboard, and verification compares hashes in constant time. Rotation replaces the nonce, revocation clears it. If the daemon key changes, the stored hash no longer matches the recomputed link: the room shows "needs a new link" instead of a wrong one. Rejected: storing the secret encrypted (same key dependency, more code) and showing the link only once at creation (hostile to "copy the link for this week's guest").

**Slug fixed at creation.** Renaming a room keeps its link working; the slug is cosmetic and never authorizes anything (the secret does).

**Migrations.** The schema was `CREATE IF NOT EXISTS` only. Adding a column to an existing table needs versioning, so `PRAGMA user_version` migrations start here with the old schema as step 1.

**Ending a meeting** is an HTTP host action that broadcasts `session_end` (the constant existed unused) and is refused while a take records, so no capture is cut by a stray click. Guests stop reconnecting; their already-granted uploads continue.

**Home.** The green room doubles as the "New meeting" card, with Rooms and Recent meetings below it, so device setup stays one step and every existing flow (and test) that opens `/` and presses join is unchanged.

### 2026-10-25: post-take transcript, vault note and clip-editor handoff (ADR-016, SL-P4-1)

**Transcript from isolated tracks.** Every export already has one WAV per participant, so StudioLink never needs diarization: it transcribes each participant's track on its own and labels the segments with that participant's name from the manifest (now carrying `participantId`). `minutes-cli` had no machine-readable, library-free way to transcribe one file. `import`/`process`/`assign` would put StudioLink media into the user's Minutes library and give back only Markdown. We added one purely additive Minutes command, `transcribe-file`, on a Minutes branch. It is stateless (dispatched before the store opens), runs the same `PipelineOrchestrator`, and writes `minutes.file-transcript/1` JSON. StudioLink calls it argv-only with a minimal environment, writing into a private 0700 folder. It shifts each track by its manifest `offsetSec`, merges deterministically, and writes JSON, Markdown (Minutes' `**Name** (M:SS): text`), and SRT/VTT cues capped at 84 characters and 7 s. The files are swapped in together under the pipeline lock, and the write is refused if the manifest changed during the run. A failed track leaves the others usable and is marked in `speakers[]`. Rejected: linking Speech/FluidAudio into the daemon (CGO, and it duplicates Minutes), and diarizing a mixdown (throws away exact speakers).

**Speech permission is the real-world blocker.** Minutes' batch path never prompts and requires Speech Recognition to be authorized for the *responsible* process. A `minutes-cli` started by `studiolinkd` is attributed to whatever launched the daemon (StudioLink.app, or a terminal). The real run here failed with "permission denied" for that reason. The likely fix is in StudioLink.app: add a usage string and a one-time attended `requestAuthorization`. It is recorded as open, not built, because it needs an attended TCC run.

**Vault note.** One note per take in Minutes' format and folder, so vault views over `#meeting` include StudioLink sessions. Re-sends PATCH with `if_updated_at` and never overwrite edits made in the vault. Credentials: by default `parachute auth mint-token --ephemeral` is minted at send time and dropped, so StudioLink stores no vault secret. A token file is accepted only as a 0600, owner-owned regular file. Redirects are not followed, and server echoes of the token are redacted. Receipts hold only note ids. Rejected: storing a long-lived token in the data dir by default, and a Keychain dependency from a CGO-free daemon.

**Clip-editor handoff.** The agentic video editor's contract is its `work/*.json` artifacts, so StudioLink writes those shapes (`transcript.json` with S1..Sn named from participants, and `sync.json` from manifest offsets with `drift_ppm 0`). They reference a program mix whose time zero is take zero. It also writes an index, `handoff/clip-editor.json`. The program mix is built by an argv builder (`BuildProgramMixArgs`, golden-tested plus a synthetic onset test). The recording pipeline is unchanged. Handoffs only read the published package, never call media.

**Routes.** Four host-only routes under `/api/v1/takes/{id}/` (`integrations`, `transcript`, `parachute`, `handoff/clip-editor`), all through `requireHost` and added to the Funnel guardrail test. Jobs run in the background, one per kind per take, and the UI polls while one runs.
### 2026-10-25: call quality is measured on the client and steers caps and uploads (SL-P0-8)

**Where quality is measured.** Each client computes its own quality from `getStats()` every 2 s and publishes it (`net_stats`), instead of the SFU estimating it from Pion interceptor stats. The client sees everything that matters for its own experience: the selected path (relay/tailnet), its bandwidth estimate, the encoder's limitation reason, and the SFU's RTCP receiver reports for what it sends. The hub only sanitizes, stamps identity and relays. Server-side Pion stats can be added later as a cross-check; they were not needed for the indicator or the policies.

**Caps.** The camera policy stays a pure function of inputs: participant count, path (relay sends one tier lower, since TURN-over-TCP through Funnel adds head-of-line blocking) and a congestion step from a reducer with hysteresis. Congestion requires `qualityLimitationReason == 'bandwidth'` *with* an estimate below our own cap, or outbound loss ≥ 5%, because Chrome also says `bandwidth` when our deliberate `maxBitrate` is the limit. Stepping up needs only that the estimate covers the current cap: an app-limited sender's estimate grows to only ~1.15× what it sends (measured), so a higher bar never let the call recover. Oscillation is handled by doubling the hold after a failed upward probe. Capture and recorders are never touched.

**Uploads.** Upload pacing follows the uplink, not the camera recovery. Coupling it to the caps step kept uploads throttled for 85 s after the network recovered in the first runs, while releasing it as soon as the call had adapted down sent uploads back to full speed and congested the call again (seen at 40 s into the impairment). So there are three live states: stressed → 1 upload paced at 25% of the estimate (15% when poor); adapted but not stressed → 1 upload at 50%; healthy → 2 (1 relayed). Stop drains at 4. The OPFS journal is the buffer, so backpressure never drops data, and request timeouts now scale with the chunk size so a slow uplink can't turn pacing into retry exhaustion.

**Test method.** CDP network emulation affects WebRTC only on sockets created while emulation was active on that session, so the impairment test pre-arms the guest with an unlimited condition before it joins. HTTP and WebRTC are throttled with separate budgets, so the test proves the policies react, not that uploads and call share one bottleneck. That needs a real constrained uplink (dummynet/`pfctl` needs root; not used).
### 2026-10-25: live captions are recognized on the host's Mac from the host page's call audio (SL-P4-2)

**Audio source.** The host's browser is already in the call and decodes every remote participant's audio as a separate WebRTC track, so it taps those tracks (plus its own mic) in an AudioWorklet and streams 16 kHz mono Int16 frames, keyed by participant ID, to a host-only ingest socket. Speaker attribution is therefore exact without diarization. Rejected: tapping in the SFU (Pion forwards Opus RTP; decoding there would add an Opus decoder to the daemon and CGO or a pure-Go decoder for no accuracy gain) and each guest sending its own mic (guests' uplinks and consent flows get involved, and Funnel guests would need a new upload path). The AGENTS guardrail ("nothing in the recording pipeline may read WebRTC-received media except refrec") still holds: captions are **not** the recording pipeline. `internal/captions` cannot import store/upload/postproc/export/refrec/align/ffmpeg/sfu, those packages cannot import it (test), and captions are never written into a take or export.

**Recognizer.** Recognition runs in a separate local **caption provider** that the daemon reaches over a loopback-only WebSocket authorized by the existing desktop token (same rules as `/api/v1/desktop/state`). This keeps the daemon CGO-free and lets Minutes implement the same documented protocol later. The provider never learns participant IDs or names, only opaque stream IDs. The Mac app's provider uses **SpeechAnalyzer + SpeechTranscriber** on macOS 26+. It is on-device by design, has no duration limit, gives volatile and final results with audio time ranges, accepts 16 kHz Int16 natively, and needed no TCC prompt in an unattended run on macOS 26.6.2. On older systems it falls back to `SFSpeechRecognizer` with `requiresOnDeviceRecognition` (fail closed), using Minutes' 12 s rotation approach. The browser's Web Speech API is rejected because Chrome sends the audio to Google.

**Fan-out and retention.** The hub broadcasts `caption` to admitted participants only. `caption_state` also reaches the waiting room, like the recording state, for transparency. Final segments are kept in daemon memory only (20 000 per meeting, the last 20 ended meetings) and offered to the host as VTT/JSON at meeting end. Nothing is persisted or logged. Limits: 16 streams per meeting, audio at most 2 s ahead of wall time, 1 s per frame, partials throttled to 150 ms, 40 results/s per stream, text capped at 500 characters with control characters folded. A stream restarts after a >2 s gap or a dropped frame, so provider timestamps never skew.

**Open.** A real multi-person session with real microphones and room acoustics; recognition quality in non-English languages; whether the host's own mic loses words to echo cancellation during double talk (seen once in a synthetic run, where the host's sentence overlapped the guest's).

### 2026-10-25: export speed is bounded by VideoToolbox H.264; ProRes Proxy is the fast option and originals ship first (SL-P0-9)

**Measurement.** A 3 × 30 min take (MediaRecorder-like VP9/Opus fMP4, 1080p) exported in 445 s; 428 s of it was `h264_videotoolbox`. On the M2 Max host that encoder does ~375 frames/s at 1080p independent of content, profile, B-frames, `-prio_speed`, pixel format or hardware decode, and concurrent sessions share the throughput (2 in parallel take 2× as long; H.264 + HEVC in parallel also serialize). Decode (0.3 s/min) and audio (0.1 s/min) are minor. So parallelizing H.264 encodes buys only overlap (measured 1.09× at 3 workers vs 1), and "≥4× faster" is not reachable with the same H.264 deliverable on this hardware. Software H.264 (libx264) is GPL and Apple's software VideoToolbox encoder (`-require_sw`) is 3× slower than hardware.

**Decision.** (1) Keep H.264 15 Mbit/s as the default editor codec (compact, unchanged deliverable) and run it with 2 concurrent sessions. (2) Add the session setting `export_codec: prores_proxy`: ProRes 422 Proxy on the separate ProRes engines, which scale with parallel sessions (1 worker 85 s, 2: 53 s, 3+: 35 s for 3 × 10 min; 4.2× faster than H.264 for three cameras), at 1.7× (busy test pattern) to 9× (static fake webcam) the bytes. Editors import ProRes natively; without VideoToolbox it falls back to FFmpeg's LGPL `prores_ks`. (3) Quick delivery: the assembled originals plus manifest/offsets download immediately (`/takes/{id}/originals`), so nobody waits for the conform to start editing. This deliberately relaxes the 2026-10-15 rule that downloads contain only published outputs: raw uploads become downloadable, still host-only, Funnel-denied and never including sidecars, the database or credentials. (4) Publish clones files on APFS instead of copying (7.7 s → 0 s at 30 min).

**Stream copy.** An H.264 4:2:0 camera that already starts at its container start, has exactly the target nominal rate, has every packet on that frame grid (all PTS checked by demuxing) and drifts less than half a frame over the take is remuxed instead of re-encoded. This keeps the CFR guarantee from the 2026-10-16 entries: a copied file is CFR by construction, and timing (offset, leading video offset 0) is identical to a conform. Rejected: copying VFR MediaRecorder files (editors misplace VFR media, the original reason for CFR), and `-itsscale` drift retiming on copy (produces 29.9996 fps media that editors conform back, reintroducing the drift). MediaRecorder output never qualifies today, so the path is for CFR recorders and imports.

**Rejected.** Mixing H.264 and ProRes angles in one package to use both engines (inconsistent deliverables), ProRes as default (silent 2–9× size growth for remote editors), streaming the editor ZIP (would drop Content-Length/Range; the temp ZIP costs ~1 s per GB after export and is unchanged).

### 2026-10-25: Meet/Riverside gaps — leave, background effects, call audio, phone camera (SL-P1-6/7/8/9)

**Leave.** Guests leave by closing their socket on purpose (no new message): the hub's normal unregister drops their tile, and their signed in-memory grant lets Rejoin resume without another admission. Recorders stop and flush first so the camera is released; uploads are page-wide and keep draining. The host gets no "leave and keep the meeting running": the hub has no host-less meeting (no host transfer, waiting guests could not be admitted, a running take could not be stopped). Rejected: a `leave` message (nothing the hub would do differently).

**Background effects only on the call sender.** One capture feeds the recorder untouched (ADR-006); a `BackgroundProcessor` turns the camera track into a ≤720p processed track that replaces the camera on the call sender (`replaceTrack`, no renegotiation). Segmentation is MediaPipe Tasks Vision 1.0.1 (Apache-2.0) with the selfie segmenter model (labels.txt: `selfie`), run on a 256-wide copy of the frame; the mask is feathered by upscaling, the background blurred on a quarter-size canvas. The WASM (11.7 MB) is copied from the pinned npm package at build time after a SHA-256 check and is gitignored in `webassets/dist` (too big to commit); the 250 KB model is committed. Compiling WASM requires CSP `script-src 'wasm-unsafe-eval'` (the only extension; `'unsafe-eval'` stays off). The CPU (XNNPACK) delegate is the default: 7 ms a frame on an M2 Max like the GPU delegate, without a GPU→CPU readback, and 4× faster where WebGL is software. "Also apply to my recording" was not built: the recorder runs at 1080p and the processor at 720p, so it would silently lower recording quality.

**Recording mic opens raw; the call gets a processed capture.** Measured in Chromium: once a device is open *with* processing, a later request for the same device with different processing gets the open source's processing (and `applyConstraints` on a clone or the original changes nothing); when the device was opened *raw*, a later processed request is processed per track. So the capture mic now opens with echo cancellation, noise suppression and AGC off — what ARCHITECTURE §4.2 always specified, and what makes the PCM track actually raw — and the call mic is a separate processed capture of the same device. Changing the call processing stops the old call capture before opening the new one (a moment of call silence). A browser that still returns the wrong processing raises `SharedProcessingError`; the capture is then reopened with the call's processing and the UI says the settings also apply to the recording (locked while recording). Consequence: the camera file's muxed audio is now raw, so speaker bleed is no longer echo-cancelled there; headphones were already the guidance.

**Phone capability.** A phone joins with a signed, 10-minute capability minted only for an admitted host/guest that is connected right now (`POST /sessions/{id}/subsource`, its own grant as bearer; Funnel allowed like the guest page). Format `phone:session:parent:nonce:exp` with a domain-separated HMAC, so no other token verifies as one and vice versa; the nonce is spent at the WebSocket upgrade (`role=subsource`), and only while the parent is still admitted. The phone's own participant grant reconnects it. The hub assigns its name ("<Parent> · Phone"), admits it without a prompt (also into a locked room), never expects it in a take, refuses everything but media/clock/status messages, and removes it with its parent. The SFU marks it publish-only (no downlink). It publishes video only (its mic would echo next to its participant) but records camera + raw room mic. Its sources stay owned by the phone participant (upload authorization unchanged; it has its own 16-track limit), and postproc attributes them to the parent with `source: "phone"` ("<Name> Phone" angle; never a speaker voice track). Limit: 2 phones per participant.

### 2026-10-26: recording mic mode (raw / clean) and the producer role (SL-P1-10, SL-P1-11)

**Recording mic mode.** SL-P1-8 made the recording mic raw for everyone, which is right with headphones and wrong on laptop speakers (everyone else's voice bleeds into that person's ISO track). Each participant now has a mode: `auto` (default), `raw`, `clean` (echo cancellation + noise suppression, automatic gain *off*, so levels don't pump in the edit). `auto` is raw when the participant ticks "I'm wearing headphones" (pre-checked in the green room while the pre-flight label heuristic sees a headphone-like device, until the person touches it; frozen at join so plugging something in mid-call never reopens the mic by surprise) and clean otherwise. The host's session/room default (`recording_mic_mode` in session settings and a room's recording preset; Settings → Recording microphone) replaces `auto` for everyone; a participant's explicit raw/clean still wins (they know their setup). Changes are locked while a take arms, records or stops, like device switching; a host change that arrives mid-take is applied when the take ends. The resolved mode plus the recording track's *measured* `getSettings()` is reported in pre-flight (`preflight.recordingMic`, an info item "Recording mic"), shown to the host per participant ("Raw mic (headphones)", "Clean mic (no headphones)", "… (host setting)", "… (chosen)") and written into every recorded track's sidecar (`micProcessing`), from where postproc copies it into `manifest.json` (camera audio and PCM sources) and the originals manifest. The uncompressed PCM mic opens with the same processing as the recording mic.

**Measured in Chromium 149 (fake devices; `getSettings()` plus a level signature where AGC is audible).** (1) With plain boolean constraints Chromium treats processing as *ideal* and hands a new request an already-open capture of the device as the "best fit": a clean recording capture made a later AGC-on call request come back with AGC off. So all mic processing is now requested with `{exact: …}`, falling back to ideal values only on `OverconstrainedError`. (2) With an explicit `deviceId` (the normal case after permission), a device has **at most one processed capture configuration open at a time**: a second, different configuration in which any of EC/NS/AGC is on is refused with `OverconstrainedError` (constraint `deviceId`), in either order (clean then call, call then clean, clean then AGC-only, …). A fully raw capture always coexists with it. (Without a `deviceId`, "default" behaves as a separate device, which is why a first probe looked fine; not usable.) Consequences: **raw** recording + processed call works exactly as SL-P1-8 built it (call toggles independent; measured raw recording `{ec:false,ns:false,agc:false}` next to call `{true,true,true}` and `{true,false,true}` with noise suppression off). **Clean** recording + a differently processed call capture cannot exist. Arrangement: in clean mode the call *shares the clean capture* (call `{ec:true,ns:true,agc:false}`), and the call-audio switches show that and are disabled with an explanation ("wear headphones to set call audio separately"). The recording is never changed to satisfy the call. Rejected: (a) the recording reusing the processed call capture (records AGC, and every call toggle would silently change the ISO track); (b) applying the call's toggles to the shared capture (same problem); (c) opening the call capture on the `default` alias (only works when the chosen mic is the system default). Ordering matters because of (2): switching the recording to clean first stops the call's own processed capture (a moment of call silence), and switching back to raw stops the old clean capture before the call reopens its own. The previous `SharedProcessingError` fallback remains for browsers that share processing even with a raw recording capture. Phones (SL-P1-9) keep their own raw room mic and carry no `micProcessing`.

**Producer.** A producer is a Riverside-style assistant: admitted to the call, heard (camera starts off, can be turned on), never recorded. Server-side: the hub never sends a producer `record_start`/`record_stop` (it learns the take from `room_state`), excludes it from the expected-recorder snapshot, the upload handler refuses its track registrations (403), the caption manager treats it as not admitted (not captioned or transcribed), so exports, originals and transcripts contain only host + guests. Powers (`requireAssist`, negative-tested per message): admit/decline *waiting guests* (never another producer, never someone admitted), start/stop takes with the pre-flight refresh, mute guests and producers (not the host), remove guests (not the host, not a producer), receive guest join requests and the host dashboard (source health, pre-flight). Not: end the meeting, lock the room, captions, screen stop, chirp, lowering hands, settings, links, livestream, exports — all host routes need a host token from a management position, which a producer never holds. A producer always waits for the host's admission, even in an auto-admit room (its link grants assist powers). **Producer link**: separate from the guest link, `hex(HMAC(daemon key, "studiolink/producer-invite/v1" ‖ scope ‖ nonce))` with scope `session:<id>` for an instant meeting or `room:<id>` for a room (so it is reused every episode like the room's guest link); only nonce + SHA-256 are stored (`producer_links`, migration 3). Rotate/revoke replace it at once and deny producers still waiting under the old one; an admitted producer stays (the host can remove them). It reaches the waiting room and the invite-level session view (`joinRole: "producer"` so the green room can say so) and the room lobby (`role: "producer"`), never a host or management route (Funnel guardrail test extended). Rejected: auto-admitting producers (a leaked link would hand out take control), letting producers admit producers (privilege escalation by chain), and a producer recording a "talkback" track (out of scope; Riverside doesn't either).

### 2026-10-26: teleprompter, branding and lower thirds (SL-P5-1, SL-P5-2)

**Where things live.** Production settings are keyed by the same scope as producer links: `room:<id>` for a meeting opened from a room, `session:<id>` for an instant meeting (`store.ProductionScope`), in one `production` table (migration 4). A room's teleprompter script is saved there and comes back next episode; an instant meeting's script is kept in hub memory only, as asked (nothing to resume once the meeting ends). Brand settings and the logo are stored for both scopes because the logo has to be served over HTTP. Lower thirds belong to a meeting's participants (`lower_thirds`, FK with cascade) so the export can read them; they are not carried to the next episode of a room (participants are new rows each meeting). Rejected: a column on `participants` (would touch every participant query other work depends on), and the room settings JSON for the script (64 KB of text in a blob every room listing decodes).

**Teleprompter visibility.** Three levels chosen by the host only: *only me* (`host`), *host + producers* (`crew`), *everyone*. The hub filters the text per recipient, so a guest's browser never receives a script it may not see, and the client clears it when visibility shrinks. A producer edits unless the host keeps the script private: "only me" means nobody else, including the producer, which keeps private notes private. Guests never edit. Scroll sync is host-only and positional: the host shares `position` as a fraction of its scroll range plus play state and speed; followers map the fraction onto their own reader (fonts and windows differ, so pixels would not match) and keep auto-scrolling locally between updates (≤ 4 per second, with a guaranteed trailing update). Speed is "lines per 10 seconds", so it reads the same at any text size.

**Logo: PNG/JPEG only, same origin.** SVG is refused outright (a document that can carry script); declared type, magic bytes and a decoded header must agree; ≤ 1 MB and ≤ 4096². The host page fetches it with the host token in a header and draws an `ImageBitmap`, so the page CSP (`img-src 'self' data: blob:`) is unchanged, no token is in a URL, and the canvas stays origin-clean for `captureStream`. **Branding in the livestream only; recordings stay clean ISO.** No burned-in "program" recording: titles go to `manifest.json` `participants[] { id, name, role, lowerThirdName, title }`. ### 2026-10-26: full-episode rehearsal; camera audio after Opus priming; PCM measured against its own camera (SL-QA-1)

**Rehearsal.** `web/tests/rehearsal.browser.mjs` (`make rehearsal`) runs one episode with every podcast-day feature at once (rooms, producer, early guests, raw/clean/PCM mics, captions, chat, branding, screen share, livestream, network impairment, PeerConnection failure, WebSocket drop, phone camera, originals during export, editor ZIP, Minutes, Parachute, end of meeting). It found the bugs below; each has its own regression test.

**Camera-embedded audio is placed at its first decoded sample.** Chromium's MP4/Opus MediaRecorder files declare 80 ms of encoder priming (`initial_padding` 3840) with no edit list. ffmpeg drops the priming and presents the first real sample at 0.08 s; a plain decode to WAV starts with that sample, so the extracted camera microphone (host, screen, phone) sat 80 ms ahead of its own video in every export. The export now adds the first decoded audio frame's time (`ffprobe -read_intervals %+#8 frame=pts_time`, golden argv) to that audio's offset, as it already did for a video stream's leading timestamp. Evidence that the timestamped placement is the true one: the independently anchored PCM capture of the same microphone agrees with it within 0–9 ms in four rehearsal runs, and disagrees by 80–89 ms with the plain decode. Fixture: a synthetic click track recorded by Chromium (`testdata/media/chromium-mp4-opus-priming.mp4`).

**PCM measured against the same microphone in the participant's own camera file.** The PCM worklet's anchor is a render-start estimate without input latency (its sidecar says so). The camera file's audio shares the microphone and its video's capture clock, so cross-correlating the two is valid where cross-device correlation is not (DECISIONS 007 still holds between people). Two 8 s windows at 8 kHz, ±0.5 s search, normalized correlation ≥ 0.6 in both, windows agreeing within 10 ms; otherwise the clock estimate stays (`sidecar-coarse`). Applied in the editor package and the originals manifest (`method: paired-xcorr`). Measured corrections in the rehearsal were 0–8 ms, so this is a safety net rather than a large correction on this machine.

**Not changed, flagged.** Drift correction uses `atempo`, which re-synthesizes the waveform (WSOLA) even for single-digit ppm: the exported "uncompressed" PCM differs from the original by roughly 10–25 dB SNR in short windows. Resampling-based correction (or leaving PCM unstretched when drift is tiny) should be evaluated with listening tests before changing the export.

**Admission order.** The dashboard listed participants in Go map order, so with several people waiting the host's banner changed names every second. It is now arrival order, and the host is offered a waiting producer first (only the host can admit one).

### 2026-10-26: drift correction resamples instead of tempo-stretching (supersedes the atempo choice)

Clock drift is a sample-clock error: a device whose clock runs at 1/B of nominal labels B seconds of sound as one second, shifting time and pitch together. Undoing it is a resample, not a tempo change. `atempo` (WSOLA) kept the drifted pitch and rewrote the waveform even for a few ppm, leaving exported "uncompressed" microphones at roughly 10–25 dB SNR against their originals (found by the SL-QA-1 rehearsal), and added a constant ~21 ms latency that STATUS had recorded as a "sparse-pulse processing offset". `asetrate` only accepts integer rates, so the ratio B is expressed as P/Q with Q in [192000, 384000] (error < 1e-9): `aresample=P → asetrate=Q → aresample=48000`. Measured: a 100 ppm–corrected 30 s tone is within 66.7 dB SNR of the ideal tone (`TestAudioDriftResamplesTransparently`); the 2-minute flash/click integration test's audio residual went from −21.2 ms to 0.03 ms at both ends, with video residuals unchanged (−2.2/−16.2 ms, within one frame).

### 2026-10-26: in-app updates use Sparkle 2, opt-in at build time and off without a key (SL-P2-2)

The Mac host app gets update readiness the way Minutes does: Sparkle 2 (2.10.0, exact pin) with an EdDSA-signed appcast; Sparkle asks on second launch before checking automatically and verifies every download against `SUPublicEDKey`. Unlike Minutes, it is a build setting. Only `STUDIOLINK_SPARKLE=1` adds the SwiftPM dependency (default builds fetch and link nothing, and `package-mac.sh` refuses a Sparkle link without it), and the updater only starts when the bundle's Info.plist carries an https `SUFeedURL` and a 32-byte base64 Ed25519 public key, supplied by `STUDIOLINK_APPCAST_URL` / `STUDIOLINK_SPARKLE_PUBLIC_KEY` at package time (`UpdateConfiguration`, unit-tested). Reasons: StudioLink is private-source and has no release feed yet; an updater that starts without a verifiable key or feed would be a liability; and a hosted appcast is a release choice for the owner, not a runtime dependency (the app works fully without it, so the "no hosted service" guardrail holds). The private EdDSA key is generated by the owner with Sparkle's `generate_keys` into their Keychain and is never stored in the repo or read by the scripts. Nothing is published by the build. With Sparkle the app is signed without `--deep` so Sparkle's XPC helpers keep their own signatures and entitlements.

### 2026-10-26: async record links (SL-P5-3, ADR-017) and the livestream bitrate (SL-P3-2)

**A submission is a session.** The pipeline after recording (upload grant checks, per-track quota, expected-recorder snapshot, assembly, postproc, originals, integrations) is keyed by session and take. Making each guest visit a session with exactly one admitted participant meant no new code on that path: the host gets a short-lived host token for a submitted submission and uses the existing take routes. The cost is that these sessions must stay out of everything call-shaped. The WebSocket refuses them (any credential, host token included), `ListRecentSessions` hides them, and `room_id` is never set on them (a link's room is kept on the link), so a room's live meeting can't be confused with a submission.

**Two credentials on the guest side.** The link secret says "you may record for this link"; the submission key says "this draft is yours". The key is 256 random bits returned once to the browser that created the draft (localStorage, per link) and stored hashed. Rotating or revoking the link refuses every guest call at once, including on existing drafts. Uploads of takes already recorded continue under their 12 h participant grant (a recording isn't lost because the host replaced a link); the host can delete a submission to stop them for good.

**Take lifecycle on the server.** The guest starts and stops takes over HTTP (no hub). Start creates a take with an expected-recorder snapshot of just that guest. The server stops it at the link's limit + 2 s (a timer, plus a sweep on every record API request for takes left by a daemon restart), which also fixes the take's upload quota. Take numbers come from a per-submission counter, so a deleted re-record never reuses an ID. Clock sync uses HTTP pings (`/clock`), so solo sidecars carry the same host-clock fit as call recordings.

**Caps.** Submitted submissions are capped atomically in one SQL statement. At most 5 drafts may be started per link per 24 h (a leaked link can't create unbounded sessions); 10 kept and 30 started takes per submission; a link-wide byte cap is checked in the upload handler under a per-link lock taken after the track lock. Opening a link and starting a submission share the join rate limiter.

**Livestream bitrate.** ffmpeg's tee muxer reports `bitrate=N/A` and `total_size=N/A` (checked with the bundled 9.0.2 build), so an output bitrate isn't derivable in production. The status now carries the browser→daemon ingest rate over a 5 s sliding window (decaying to 0 when ingest stalls instead of freezing at the last value) as `bitrateKbps` with `bitrateSource: "ingest"`, and an output rate from `total_size` deltas when an ffmpeg does report it (`bitrateSource: "output"`). The encoder's configured target is not reported as if it were a measurement.

### 2026-10-26: calendar integration through files, template links, a tailnet feed and EventKit (SL-P6-1, ADR-018)

**UTC, not VTIMEZONE.** Every `DTSTART`/`DTEND` is UTC. A one-off meeting needs no time-zone rules, and UTC avoids shipping (and keeping correct) VTIMEZONE blocks. The host's IANA zone is stored only for human-readable text ("Friday, October 30, 2026, 10:00 AM – 11:30 AM PDT (America/Los_Angeles)") and the Google `ctz` parameter; the daemon embeds `time/tzdata` so this never depends on the machine's zoneinfo.

**PUBLISH unless it's a real invitation.** RFC 5546 REQUEST needs an ORGANIZER. StudioLink doesn't know the host's address unless they type it, so the default `.ics` is PUBLISH (an event to add, no attendee list). With an organizer email and guest emails it becomes REQUEST, so RSVPs go to the host's own mailbox, not to StudioLink. Cancellation is METHOD:CANCEL + STATUS:CANCELLED with a higher SEQUENCE; without an organizer some clients may only mark the event cancelled rather than remove it (not yet checked on real clients).

**The feed is the host's, so it's tailnet-only.** A subscription feed carries every upcoming meeting with its guest link. Serving it through Funnel would let Google Calendar subscribe, but it would also put the feed on the public internet behind nothing but a URL. The feed refuses the Funnel marker even with the right key and accepts only loopback or private Serve from a tailnet address. Google users get per-meeting template links, or the Mac app writes events into a Google calendar added to macOS.

**EventKit full access, asked only from Settings.** Matching needs to read events, and write-back needs to find its own events again to update or remove them, so write-only access isn't enough. The permission prompt appears only when the user turns on a calendar toggle (both off by default), and every path degrades to "scheduled meetings from the daemon only" without it. Matching compares the slug and this host's guest origins; it never reads or stores the link token.

### 2026-10-26: post-take transcripts get a built-in on-device engine; Minutes becomes optional (SL-P4-3, amends ADR-016)

**Why not wait for Minutes.** ADR-016 routed transcripts through `minutes-cli transcribe-file`, which exists only on an unmerged Minutes branch and is blocked by Speech Recognition attribution for a CLI child. The StudioLink Mac app already runs Apple's `SpeechAnalyzer`/`SpeechTranscriber` for live captions, and on macOS 26 that API needs no TCC grant (observed again for files, below). So the app also transcribes files, and that is the default engine. The Minutes path is kept intact as an optional engine that can be chosen only when a compatible CLI is detected (the `help` probe for `transcribe-file`).

**A sibling socket, not the caption socket.** File jobs use `/api/v1/transcription/provider` with the caption provider's rules (direct loopback, desktop token, no Origin, one provider, hello first) but a separate package (`host/internal/filespeech`) and a separate app setting. Live captions are call audio and must stay out of the recording pipeline; post-take transcripts read the published export. Sharing one socket would have coupled the two (and made transcripts depend on the live-captions toggle). `filespeech` imports nothing from the module, and guardrail tests forbid imports between captions, filespeech, integrations, transcript and the recording packages.

**Path, not audio, over the socket.** The daemon sends an absolute path to the WAV inside the published package and the app opens it with `AVAudioFile` and `SpeechAnalyzer.start(inputAudioFile:finishAfterFile:)`. This handles any export format (48 kHz/24-bit, camera audio) without a Go resampler and runs much faster than real time (a 62-minute WAV in 92 s, one request, no chunking). The app runs as the same user on the same Mac and is not sandboxed; the job path is validated (absolute, no `..`, audio extension, regular file). Rejected: streaming PCM like captions (needs WAV decoding/resampling in a CGO-free daemon and real-time-ish pacing), and linking Speech into the daemon (CGO).

**Same document.** Both engines feed one engine-neutral track result into the unchanged `transcript.Merge`/`Write` and handoff code, so `transcript.{json,md,srt,vtt}`, the Parachute note and `handoff/ave/transcript.json` are identical except `engine` (`studiolink-builtin` / `minutes-cli`). The provider sends final phrases with word ranges and confidences (segment confidence = mean word confidence, omitted without words), the daemon validates every number and folds text.

**Robustness.** One job at a time per provider (daemon-side queue); cancel is acknowledged by the provider before the next job is sent; a 3-minute idle timeout; a disconnect fails the running track with an actionable message. Per-track progress is published in the job detail. Finished tracks of a failed or cancelled run are kept in memory keyed by engine + manifest hash + source, so a retry redoes only the rest and a re-export invalidates them. Nothing is written to the package unless the run reaches the merge. A silent track is a success with no segments. Auto-transcribe that can't start now shows an error state instead of only a log line. The pre-macOS 26 fallback (`SFSpeechRecognizer`, on device only) needs a Speech Recognition grant: the app declares `NSSpeechRecognitionUsageDescription` and offers an Allow button; without it the provider announces `not_authorized` and the host sees what to do. That fallback chunks audio at ≤ 50 s at quiet points because of its request limit.

### 2026-10-26: the clip-editor handoff carries ave's camera mapping, and ave learns to import it (SL-P4-4)

Running `ave` on a real StudioLink export showed the handoff was missing the one thing every import needed by hand: `episode.json`'s camera/speaker mapping. StudioLink knows it exactly (each camera is its participant's webcam), so the package now carries it in ave's shape (`handoff/ave/episode.json`): camera `C<n>` for speaker `S<n>`, `role` host/guest from the manifest participants, `session: "s1"` on every camera (ave groups cameras into sessions by creation time and duration; StudioLink's files have no creation time and a late joiner's camera is shorter, which would split one take into two sessions), and `audio_source: raw/program.wav`. Screen shares and further cameras are `extra_angles`, never cameras, because ave's cleanup cuts away to any non-wide camera. The mapping is still a human checkpoint in ave; StudioLink only removes the typing.

Speaker ids are host first, then manifest order (they followed whichever microphone the manifest listed first). `work/transcript.md` is written in ave's own format, and the transcript's `engine.asr` names the recognizer that actually ran.

**Where the import lives.** ave gets `ave import-studiolink` (branch `feat/studiolink-import`, not merged): one command that copies, places, maps, probes and checks. StudioLink ships `scripts/ave-import.sh`, which uses that command when present and the manual recipe with a stock ave. Keeping the importer in ave keeps ave's rules (raw is read-only, existing work files and episode keys win) next to the code that enforces them; StudioLink only promises the file shapes, which `TestHandoffLoadsInAve` checks against ave's own loaders.

**Not changed in StudioLink: take zero.** Cameras start 20–50 ms after take zero (each browser's recorder starts on its own), and stock ave's planner refuses a single-session episode with no camera at episode time 0. Moving StudioLink's time origin would break the manifest, the editor XML and the transcript, which all agree on take zero. The fix went into ave instead (`late_start_max_s`: start the cut list once every speaker camera rolls when that is within 1 s; unchanged when a camera is at 0). Stock ave works with `--session s1`.

### 2026-10-26: the daemon publishes RTMP(S) itself; ffmpeg only encodes (ADR-019, SL-P3-3)

**Why ffmpeg could not keep the key.** Two requirements met in one place: the stream key must not appear in `ps`, and one dropped destination must reconnect without the others noticing. Both point away from ffmpeg's `tee`. ffmpeg 9.0.2 was checked directly: its `-/option file` syntax works only for ffmpeg's own CLI options, so `-/rtmp_playpath keyfile` is "Unrecognized option"; a `-fpre` preset file with `rtmp_playpath=KEY` parses (the debug log shows it being set) but the RTMP protocol never receives it, and the listener sees an empty stream name. There is no environment variable or pipe for an output URL. And a `tee` slave that fails with `onfail=ignore` is gone until ffmpeg restarts.

**What replaces it.** ffmpeg writes FLV to stdout (`-flvflags no_duration_filesize -flush_packets 1 -f flv pipe:1`, progress on fd 3). The daemon splits that into FLV tags, keeps the metadata and both sequence headers of the current encoder run, and hands every media tag to each destination's publisher without blocking. A publisher dials only once media exists, sends the headers, starts at the next keyframe with timestamps re-based to 0, and owns its retry loop. A browser reconnect starts a new encoder run: publishers stay connected, send the new headers and continue one frame after the last timestamp they sent, so a compositor hiccup doesn't drop the platforms. A slow destination's queue is capped at 4 s; past that it skips to the next keyframe and says so ("the upload can't keep up"), which also removes the old "a stalled tee slave slows the others" limit.

**RTMPS.** TLS is Go's `crypto/tls`, which on macOS verifies through the system trust store (Security framework), with SNI set to the host as YouTube requires. There is no "skip verification" option anywhere. Tests trust a generated self-signed root through `Options.TLS`; the browser suite does the same through the daemon flag `--livestream-test-ca`, which adds to (never replaces) the system roots and logs a warning. The earlier Secure Transport stall through a local TLS proxy no longer matters: ffmpeg does no networking.

**Rejected:** a loopback relay where ffmpeg publishes `rtmp://127.0.0.1/app/<nonce>` and the daemon rewrites the publish command (needs the same chunk parser plus process supervision, and the nonce is still a usable credential in `ps` until consumed); N `-c copy` publisher processes (keys back in argv); `tee` with `use_fifo=1` and fifo recovery (keys in argv). The cost of the choice is a new RTMP client (about 600 lines, plus 190 for AMF0) instead of ffmpeg's; it is tested against ffmpeg's own RTMP listener, plain and behind TLS, and against a scripted server (rejections, pings, chunking with extended timestamps). Real YouTube, Twitch, Facebook and LinkedIn ingest is an owner test.

### 2026-10-26: acoustic verification against the host's received microphone; editor timelines checked against the FCPXML DTD (SL-P0-10)

**What ran before (and why).** ADR-007's GCC-PHAT stage was never built, not abandoned by a decision. `refrec` existed, but `StartRecording` had no caller, so no reference was ever written; the planned `rtpmap.json` (RTP time → host time) did not exist; `AlignTrackWithReferenceConfig` ignored its sample arguments. The 2026-10-14 repair audit therefore advertised clock-only (`sidecar-coarse`) alignment "until timestamped references … justify a stronger claim", and SL-QA-1 added the only acoustic step, `paired-xcorr` (a PCM mic against the same mic in the person's own camera file). Cross-device placement rested entirely on each device's clock fit.

**Reference capture.** While a take runs, the hub starts `refrec` for the session (`takes/<take>/refs/`). The SFU hands it every participant's received camera-microphone packet (never screen audio). Per participant it writes the Ogg file plus a packet log (SSRC, RTP timestamp, host arrival time, samples) — the timestamp map the old design lacked. Writing is asynchronous (bounded queue, drops instead of blocking the forwarding loop). Producers are refused (`Hub.RecordsReference`): they are never recorded, not even as a reference. This is the only recording-pipeline reader of WebRTC media (AGENTS.md), used for alignment only and never exported.

**Measurement (`align.VerifyAcoustic`).** Per SSRC, host time is fitted to RTP time along the lower envelope of arrival delays (2 s bins, trimmed line fit), so jitter, retransmission bursts and stalls only lift the envelope. Decoded samples are mapped through the log (Ogg pre-skip 3840) onto the host timeline, so loss and reconnects (new SSRC/RTP base) leave gaps, not shifts. Up to 16 windows of 8 s (16 kHz, from 1.5 s into the local file) are compared by GCC-PHAT (100–6000 Hz) within ±350 ms; a window counts with peak-to-sidelobe ≥ 4, ≥ 90 % reference coverage and speech energy. Theil–Sen slope and median level of the per-window delays give the delay at mid-take and the residual drift. The anchor is the person's camera file when it has audio (its video and the paired PCM move with it), else their audio track.

**What it can and cannot claim.** The reference delay D = send path (WebRTC capture buffering, the 20 ms Opus frame, encoder lookahead — 6.5 ms for libopus, measured through the real codec) + one-way network delay. D is not observable from the host. It is modelled as `SendPathMs` + rtt/2, with `SendPathMs` = 12 ms calibrated as the median delay of Chromium participants whose placement is healthy (10.6, 11.7, 12.7, 16.4 ms in two 1-minute rehearsals; 10.3/12.9 and 14.2/18.3 ms in two 3-minute runs; median of all eight 12.8 ms). That calibration folds in any constant bias of Chromium's recorder anchors, so "error ≈ 0" means consistent with a healthy Chromium participant, not sample-accurate against the physical capture. Hence: |error| ≤ 20 ms → **verified** (clock kept); 20–250 ms with all gates passed → **corrected** (offset replaced, method `refrec-gcc-phat`, residual reported as ±20 ms); beyond 250 ms → **disagrees** (clock kept, README tells the editor to check by ear); otherwise **unmeasurable**. The residual drift is reported (`driftPpm`), not applied: no real-device evidence yet that audio and video of one file should be stretched differently. Other browser engines may differ from Chromium by more than the 20 ms band; until measured, a Safari/Firefox guest could be "corrected" by their engine's send-path difference, which is why corrections are reported with their uncertainty.

**Evidence.** Synthetic signals (align tests): injected clock errors −85…+180 ms recovered within 0.1 ms; ±150/80 ppm drift within 0.3 ppm; 5 % loss, 15 ms jitter, a reconnect and guest bleed handled; silence and an unrelated voice never verify or correct. Real codec: libopus 20 ms packets through refrec/Ogg/ffmpeg, injected 0 and 45 ms → errors 6.56 and 51.56 ms (the 6.5 ms is libopus lookahead). End to end (`TestProcessTakeVerifiesAndCorrectsFromReference`): a mic placed 60 ms early is moved to within 1.5 ms, an accurate one is verified and left alone. Fake-device rehearsal, 3-minute take with network impairment and a PeerConnection failure: Host verified (+0.65 ms, 16/16 windows, spread 0.01 ms, drift +24 ppm), Guest B verified (−1.85 ms, 15/16, drift −7 ppm); the two measured delays differ by 2.6 ms (4.0 ms in a second 3-minute run: +2.1 / +6.1 ms), which bounds their relative cross-device error (same browser build, same machine). Guest A (raw mic) is correctly unmeasurable: Chromium's fake device replays the WAV independently per capture (~1.2 s apart, drifting ~1000 ppm), so A's separate call capture is not the same sound as its recording. On real hardware both captures come from one microphone; that, and real networks/devices, remain unmeasured.

**Editor timelines.** Apple's FCPXML DTD is "All rights reserved" (it ships in Final Cut Pro; CommandPost redistributes copies but cannot relicense them), so it is not vendored and tests do not fetch it. `export/fcpxml_dtd_test.go` transcribes the 1.10 content models, attributes, `#REQUIRED`s and enumerations of every element we write and adds Final Cut's timing rules; the full DTD was run once with `xmllint --dtdvalid` on 24 generated variants (all valid). Fixed: a camera that started before the take mark produced a negative angle offset (DTD-valid, illegal storyline) and a negative FCP7 `<start>` → the whole timeline now shifts by whole frames; durations were rounded up past the media → floored; microphones lost up to half a frame → the FCPXML keeps them sample-accurate (`start` head trim in 1/48000 s; FCP7 XML stays frame-quantized); audio clips referenced the video format → none; no audio roles → `dialogue` (screen audio `effects`); silent camera assets declared `audioRate`; audio assets lacked `audioSources`/`audioChannels`. FCP7 XML: `file://localhost/` pathurls as Premiere writes them, sequence `id` and `timecode`, `enabled`, per-file `timecode`, `sourcetrack`, `channelcount`, anamorphic/field dominance; structure checked in `export/xmeml_test.go`. Final Cut and Premiere are not installed; Resolve import of these versions waits on `scripts/resolve-acceptance.py` (needs Resolve running with scripting allowed).

### 2026-10-26: abandoned record-link drafts expire; rooms remember lower thirds by name (SL-P5-4)

**What counts as activity.** A draft's last activity is the latest of its creation, a take start and a chunk upload. Opening the page or reading the draft doesn't count: a guest who comes back and records (or whose upload resumes) moves it; one who only looks doesn't. Timestamps are parsed, not compared as text, because older rows were written in local time.

**Two thresholds, two uses.** A draft is *abandoned* (listed in Home → Recordings, deletable by hand, one or all) after 24 h without activity, the window the per-link draft cap already treats as abandoned, or as soon as its link is expired or turned off and the upload guard has passed. It *expires* (deleted on daemon start and daily) after 14 days without activity, or 24 h after its link is expired or turned off. The 24 h grace on closed links, rather than deleting at once, is deliberate: a host who extends an expired link the same day keeps the guest's unsent takes, and the guest's browser can still resume them. Defaults are flags: `--record-draft-expiry-days` (0 turns automatic cleanup off), `--record-draft-closed-link-hours`, `--record-draft-upload-guard-minutes`.

**The upload guard is absolute.** A draft with a take recording, or a take start or chunk upload in the last 60 minutes, is never deleted, by hand or automatically. The check and the row delete are one SQLite transaction under the record-link lock, so an upload that lands first keeps the draft; files are removed after the rows. Submitted recordings are never touched by any of this; only the existing per-recording Delete removes one.

**Lower thirds remembered per room, keyed by display name.** A meeting's lower thirds stay per participant (participant IDs are new every episode). A room also remembers the last name/title set for each person, keyed by the case-folded, whitespace-collapsed display name they join with, and copies it into the meeting when they are admitted (unless the meeting already has one for them, so an edit made during the episode wins and a reconnect doesn't undo it). Clearing both fields forgets it. The display name is the only stable identity a guest has (no accounts); two guests with the same name in one room share a remembered title, which the host can see and edit in Home → Rooms → Saved titles. An instant meeting remembers nothing.


## 2026-10-26 — Safari and Firefox guests [SL-P1-12]

**Codec.** Measured with Playwright 1.61.1 (WebKit 26.5, Firefox 151): WebKit’s offer lists H.264 `640c1f` (High) first; Playwright's Firefox lists only VP8/VP9/AV1 (no OpenH264). Before the change WebKit published H.264 (observed in the first run, where Chromium decoded it); a Firefox without H.264 can't decode that, and Pion would have failed that subscriber's renegotiation. With VP8 first in every client, all three engines sent VP8 (`outbound-rtp` codec) and everyone decoded everyone. The SFU guard (`sfu/codecs.go`) is a backstop: it never transcodes, it only keeps one bad pairing from failing that subscriber's whole renegotiation.

**Storage.** Safari added `FileSystemFileHandle.createWritable` only in Safari 26 (per WebKit's release notes; only WebKit 26.5 was run here, where it exists); earlier Safari has OPFS writes only through a worker's `FileSystemSyncAccessHandle`, so the suite removes `createWritable` to exercise that path. Private windows (and Playwright's ephemeral WebKit contexts) reject `navigator.storage.getDirectory()` with `UnknownError`. Chosen: probe once per page, prefer `createWritable`, fall back to a worker, and finally to memory (fragments freed once the host acknowledges them). Rejected: refusing to record in a private window (loses the guest), IndexedDB as a third journal (another storage engine and recovery path for a case that already uploads progressively).

**Timing.** Firefox and Safari coarsen `performance.now()` (1 ms or more). A localhost clock ping then measured 0 µs round trip, the client reported `rttP10Ms: 0` and the host refused to align the track ("clock fit has no measured timing samples"). The client now reports at least 1 µs for a measured sample; the host's rule is unchanged.

**Firefox WebM.** Firefox's MediaRecorder writes live WebM without a Segment Duration and ffprobe reports none, which failed export ("invalid duration format"). `ProbeMedia` now measures such files from their packets (pts + duration), without decoding.

**Testing Safari on macOS.** Playwright's WebKit enumerates mock capture devices but `getUserMedia` never resolves on macOS (no grantable camera/microphone permission, headless or headed), so the WebKit pages get a page-level synthetic capture (canvas + oscillator). Firefox uses its own fake devices through real `getUserMedia`. iOS autoplay is simulated in the iPhone suite. What this cannot prove is listed in PARITY.md.

**MediaPipe telemetry.** Tasks Vision 1.0.1 posts usage logs to `odml.pa.googleapis.com` once a minute while a segmenter exists. The CSP already blocked it (no data left), but Firefox logged each attempt; `blockMediaPipeTelemetry()` refuses that one URL before any network so the logger stops itself.

### 2026-10-26: the uncompressed mic records on the capture clock where the browser allows it (SL-QA-2, amends ADR-009)

**What broke.** The full-episode rehearsal failed at 10 minutes ("Guest A: mic vs camera audio not comparable", shifts 20 → 220 ms, then no match within ±300 ms). Both guests' PCM originals were short of the take: 599.2 s for 600.5 s of sidecar wall time (A and B alike, the same intervals at the same moments), while the camera files, recorded by MediaRecorder from the same capture, were continuous. Matching each file against the fake microphone's looping WAV located the losses: none in any camera file; in both PCM files 84–164 ms jumps from about +115 s and a steady loss after +320 s. The previously certified commit (7509783) lost 2.3–2.6 s in the same run length, so this was not a regression of the 2026-10-26 merges: the earlier 10-minute pass did not hit it.

**Why.** ADR-009's PCM path (an AudioWorklet behind `createMediaStreamSource`) gets microphone samples when the *output* device renders. Under CPU load (four Chromium instances encoding and decoding video) render callbacks are missed, the render clock falls behind wall time and Chromium drops the microphone input queued for it. Sample index stops being a clock.

**Decision.** Where `MediaStreamTrackProcessor` exists (Chromium), `LocalPcmRecorder` reads `AudioData` frames from the capture track (`engine: "track-processor"`): every captured sample, at the device's rate, with capture timestamps. Capture gaps of ≥ 15 ms are filled with silence so the file keeps the capture timeline (never drift-corrected, never trimmed). Safari and Firefox (no audio track processor) keep the AudioWorklet engine. The PCM capture is still the participant's own local microphone; nothing reads received WebRTC media. The verification run then showed the same moment from the camera side: a machine-wide capture hiccup at +414.7 s made Chromium's MediaRecorder write one long Opus packet (90 ms of timeline for 60 ms of samples) in every camera file, and the host's exported mic, converted sample by sample, sat 30 ms ahead of its camera from there on. Postproc's WAV conversion now keeps container timestamp gaps over 15 ms as silence (the threshold the PCM recorder uses), so the camera audio, the PCM and the video share one capture timeline. Rejected: padding silence into the AudioWorklet file when its render clock lags (the dropped microphone audio stays lost and the padding point is only approximate); loosening the rehearsal's ±20 ms / corr ≥ 0.5 check (it measured a real defect).
